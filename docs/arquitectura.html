1. Idea

1.1 Problema

En David Orozco Barbería y Peluquería los turnos se anotan a mano, con lápiz, en un cuaderno que lleva la estilista. La barbería atiende unos cinco clientes al día en turnos fijos de una hora, de lunes a sábado.

Mientras la agenda viva en un solo cuaderno:

  • El cliente solo puede pedir turno hablando con alguien que tenga el cuaderno a la mano. No puede ver por sí mismo qué horas quedan libres.
  • Nada impide anotar dos clientes en la misma hora con el mismo profesional, ni dar un turno en la hora de almuerzo.
  • El cuaderno no lleva la cuenta de las inasistencias. La regla que David quiere aplicar (bloquear al cliente después de dos faltas) depende de que alguien lo recuerde.
  • Los clientes no reciben ningún recordatorio, y la información de precios y formas de pago solo se da en persona.

Solución: un bot de Telegram donde el cliente agenda, consulta y cancela sus turnos a cualquier hora, conectado a una API en Laravel que aplica las reglas de la barbería. Un panel web le muestra a David y a la estilista la agenda, los clientes y las métricas.

1.5 Requisitos no funcionales

  • Seguridad: HTTPS en producción, tokens Sanctum para la API, contraseñas con hash y permisos por rol. El archivo .env nunca se sube al repositorio.
  • Consistencia: la reserva de un turno se valida dentro de una transacción con bloqueo, para que dos clientes no tomen la misma hora.
  • Tolerancia a fallos: el bot responde aunque la API no esté disponible, vuelve a iniciar sesión ante un 401 y muestra el mensaje de los 422. Si la IA falla, el cliente sigue agendando con botones.
  • Usabilidad: panel responsive con páginas 404 y 500 propias. Mensajes del bot cortos y en español de Colombia.

1.6 Reglas de negocio

IDReglaDónde se aplica
RN1Disponibilidad. Solo se ofrecen turnos de 1 hora en punto dentro del horario del profesional, fuera del descanso (12:00 a 14:00) y fuera de los cierres registrados.TurnoService
RN2Sin cruces. Al crear o reprogramar, la hora se vuelve a validar dentro de una transacción con bloqueo de fila. Si otro cliente la tomó antes, la API responde 422 y el bot ofrece las horas que quedan.CitaService, CitaRepository
RN3Anticipación. Se agenda con al menos 1 hora y hasta 14 días adelante. Cancelar con menos de 2 horas cuenta como inasistencia.CitaService
RN4Bloqueo por inasistencias. Con 2 inasistencias el cliente queda bloqueado 14 días y no puede agendar (422). Al vencer el plazo se desbloquea solo; el administrador también puede desbloquearlo antes.CitaService, middleware liberar.bloqueos
RN5Cierres. El administrador registra cierres de un día completo o de unas horas, para uno o ambos profesionales, y esas horas dejan de ofrecerse.TurnoService

2. Modelo C4

Persona Sistema propio Contenedor Componente Sistema externo

2.1 Nivel 1: contexto

TurnoBarber se relaciona con tres tipos de persona y con dos sistemas externos: Telegram, donde vive el bot, y Ollama, el modelo de IA que interpreta el texto libre.

2.2 Nivel 2: contenedores

El sistema tiene cuatro contenedores. La aplicación Laravel, el bot y la base de datos corren como servicios separados en Railway. El proxy de IA corre en el Mac del desarrollador, junto a Ollama, y se publica con un túnel de Cloudflare. El bot es el cliente externo del proyecto: vive en la carpeta /cliente, fuera de Laravel, y solo habla con la API por HTTPS.

2.3 Nivel 3: componentes de la aplicación Laravel

La aplicación separa responsabilidades en capas. Las rutas aplican la autenticación y el rol. Los controladores reciben la petición, la validan con un Form Request y delegan las reglas a un servicio. Los servicios usan repositorios para leer y guardar. La API responde con API Resources y el panel con vistas Blade.

Endpoints de la API

Todas las rutas, salvo el login, exigen un token Sanctum. El usuario del bot tiene el rol Bot; las escrituras sobre profesionales y el borrado de citas son solo del rol Administrador.

3. Modelo entidad-relación

El modelo tiene siete entidades de negocio y una tabla pivote. Incluye los tres tipos de relación que pide el proyecto:

  • 1:1: users y profesionales. Cada profesional entra al panel con su propia cuenta.
  • 1:N: roles→users, profesionales→horarios, profesionales→citas y clientes→citas.
  • N:M: cierres y profesionales, a través de cierre_profesional. Un cierre puede afectar a uno o a los dos profesionales.
